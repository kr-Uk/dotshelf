# Push Study Note

깃에 올릴 변경분만 골라서 한국어 학습 문서를 생성한다. 목적은 "커밋을 언어화해서 본인의 학습 자산으로 남기기"다.

## 언제 쓰나

사용자가 다음을 요청할 때:
- "push 전에 학습 문서 만들어줘"
- "이번 작업 정리해줘" (push 문맥에서)
- "커밋 올리면서 공부용으로 문서화"
- "PR 올리려는데 학습 자료도 같이"
- `dotshelf-commit` 스킬이 push 단계 전에 이 스킬을 제안/호출

트리거가 불명확하면 사용자에게 "push할 변경분 범위"를 먼저 확인한다. 이 스킬의 입력은 항상 **range(커밋 구간) + diff**이며, 둘이 확정되지 않으면 진행 의미가 없다.

## 기존 study-changelog와 관계

`study-changelog`는 사용자가 임의 범위를 골라 회고할 때 쓰는 범용 버전. 이 스킬은 **push 워크플로우에 결합된 자동화 버전**이다. 출력 형식과 철학은 유사하되, 입력 범위 결정과 저장 위치가 고정돼 있다.

출력 품질을 높이는 공부거리 섹션 작성 철학은 양쪽이 같다.

---

## 전체 워크플로우

```
범위 결정 → diff/커밋 수집 → 섹션별 분석 → Markdown 작성 → 저장 → (선택) 사용자 리뷰
```

### 1단계: 범위 결정

기본값:
```bash
git fetch origin
BASE=$(git merge-base HEAD origin/dev 2>/dev/null || echo "origin/dev")
RANGE="${BASE}..HEAD"
```

상황별 조정:
- **브랜치가 origin에 이미 올라가 있고 증분 push인 경우**: `origin/<현재브랜치>..HEAD`
- **로컬 신규 브랜치**: `origin/dev..HEAD` (dev에서 분기 가정)
- **master 기준 작업**: `origin/master..HEAD`
- **특정 커밋 지정**: 사용자가 "어제 커밋부터" 등 명시하면 그걸 사용

범위가 비어있으면(커밋 0개) 중단하고 "push할 변경이 없습니다"라고 알림.

### 2단계: 데이터 수집

```bash
git log --pretty=format:"%h|%s%n%b%n---" $RANGE
git diff --stat $RANGE
git diff $RANGE -- '*.java' '*.kt' '*.ts' '*.tsx' '*.py' '*.sql' '*.yml' '*.yaml' 'build.gradle*' 'pom.xml' 'package.json'
```

큰 diff는 파일별로 분할해 보고, 생성물(generated, build/, node_modules 등)은 제외한다.

**중요한 읽기 순서:**
1. 커밋 메시지로 큰 그림 파악
2. `--stat`으로 규모와 영향 범위 파악
3. 실제 diff로 세부 구현 확인
4. 필요하면 변경된 파일 주변 기존 코드도 읽어서 맥락 보강 (왜 이 구조가 필요했는지)

### 3단계: 섹션별 분석

문서는 "무엇을 했나 / 왜 했나 / 어떻게 구현했나 / 무엇을 배웠나 / 더 공부할 것"으로 간다. 각 섹션을 의식적으로 분리해 기록하면 본인이 나중에 다시 봤을 때 학습용으로 쓸 수 있다.

#### 섹션별 초점

- **무엇을**: 기능/모듈 단위로 그룹화된 변경 목록. 단순 파일 나열이 아니라 "사용자 입장 효과" + "시스템 관점 효과" 둘 다.
- **왜**: 티켓, 커밋 메시지, 주석에서 힌트 수집. 가능하면 `커밋 메시지 → 코드 → 배경`까지 이어 설명.
- **어떻게**: 핵심 코드 조각을 인용하며 구현 결정 설명. 라이브러리 선택 이유, 알고리즘, 패턴. 가벼운 변경이면 짧게, 구조적 변경이면 길게.
- **배운 것**: 이 변경을 해내기 위해 본인이 새로 알게 된 것 위주. 기술 용어 정의, 프레임워크 동작 원리, 실수에서 배운 것.
- **더 공부할 것**: 변경에 얕게 닿은 개념 중 본인이 깊게 모르는 것. "QueryDSL Projections vs JPQL DTO 생성자 — 언제 뭐 써야 하나" 같은 구체적 질문 형태로.

### 4단계: Markdown 작성

#### 템플릿

```markdown
# {한 줄 제목 — 브랜치 목적을 요약}

- **브랜치**: `feat/be/xxx`
- **범위**: `origin/dev..HEAD` (커밋 N개)
- **기간**: YYYY-MM-DD ~ YYYY-MM-DD
- **티켓**: S14P31F206-XXX (있는 경우)

## TL;DR
<3~5줄로 한 번에 요약>

## 무엇을 했나
### 1. {기능/모듈 이름}
- 사용자 관점 효과: ...
- 시스템 관점 효과: ...
- 주요 파일: `src/.../Xxx.java`, `src/.../Yyy.java`

### 2. ...

## 왜 했나
<티켓/커밋/코드 주석에서 근거 종합해서 한두 문단>

## 어떻게 구현했나

### {핵심 주제 1}
{구현 결정과 근거}

\`\`\`java
// 핵심 코드 조각
\`\`\`

핵심 포인트:
- ...

### {핵심 주제 2}
...

## 배운 것
- **{주제}**: {한 줄 요약과 핵심 개념}
  - 디테일: ...
- **{주제}**: ...

## 더 공부할 것
- [ ] {구체적 질문 형태} — 참고: {링크나 키워드}
- [ ] ...

## 참고
- 관련 커밋: abcd123, efgh456
- 관련 이슈: #...
- 관련 문서: {있으면}
```

#### 작성 원칙

- **한국어 기본**. 코드/용어는 영어 그대로.
- **코드 인용 시 핵심만**. 50줄 복붙 금지. 10~20줄 이하로 잘라 "왜 이 조각이 중요한가"를 앞뒤 문장으로 설명.
- **단정하지 않고 학습 기록임을 유지**. "이게 정답"보다 "이렇게 결정했다 / 이런 대안도 있었다" 같은 톤.
- **추상적 일반론 금지**. "좋은 아키텍처" 같은 빈 말보다, "`BaseEntity`의 `@MappedSuperclass` 때문에 상속받은 엔티티에서 auditing이 자동 적용됨" 같이 구체적으로.
- **"공부할 것"을 빈 리스트로 두지 않는다**. 반드시 2~5개는 채운다. 변경에서 본인이 깊이 모른 부분을 정직하게 꺼낸다.

### 5단계: 저장

```
<프로젝트 루트>/docs/study/{YYYY-MM-DD}-{브랜치-슬러그}.md
```

예: `backend/docs/study/2026-04-15-feat-be-user-signup.md`

- 프로젝트 루트는 `gradlew`, `pom.xml`, `package.json` 있는 곳을 기준으로 추정. 못 찾으면 현재 디렉토리.
- `docs/study/` 디렉토리가 없으면 생성.
- 동일 파일명 존재 시 `-2`, `-3` suffix.

### 6단계: 사용자 리뷰 (선택)

저장 후 사용자에게 경로와 요약을 제시:

```
📝 학습 문서 생성 완료: backend/docs/study/2026-04-15-feat-be-user-signup.md

섹션: TL;DR / 무엇을(3개) / 왜 / 어떻게(2개 주제) / 배운 것(4개) / 더 공부할 것(3개)

검토 후 수정 원하시면 알려주세요. "공부할 것"을 더 파내려가거나, 특정 섹션을 확장할 수 있습니다.
```

## dotshelf-commit과의 연동

`dotshelf-commit`이 push 단계를 진행할 때, push 직전에 이 스킬 호출을 제안할 수 있다. 체인 예시:

```
커밋 완료
→ (dotshelf-verify) 로컬 검증 통과
→ push 하기 전에: "학습 문서 생성할까요? (docs/study/에 저장)"
→ 사용자 Yes → 이 스킬 실행 → push 진행 → MR까지
→ 사용자 No → 바로 push
```

문서는 **push 전**에 생성하는 편이 좋다. push 후 생성해서 별도 커밋으로 올리면 다시 push가 필요하고, 본체 MR에 학습 문서가 포함되지 않기 때문. 다만 docs/study 파일은 본체와 같은 MR에 섞으면 리뷰가 어수선해지므로, **별도 커밋(Type: Docs)으로 본체 커밋 뒤에 추가**하는 것을 권장. `dotshelf-commit`과 함께 쓰면 자동으로 그 커밋을 생성하고 함께 push.

## 자주 마주치는 상황

**커밋이 너무 많아서 다 커버하기 어려움**
→ "핵심 커밋 3~5개만 깊게, 나머지는 TL;DR에 한 줄씩". 학습 목적이라 양보다 질.

**단순 설정/린트 변경뿐**
→ 학습할 게 적으면 스킵 제안: "이번 push에는 학습 포인트가 크지 않아 보입니다. 문서 생성 건너뛸까요?"

**마이그레이션/Flyway 추가가 있음**
→ 스키마 변경의 **이유**와 **마이그레이션 전략**을 "어떻게"에 상세히. 데이터 백필 필요 여부, 다운타임 영향 등을 꼭 언급.

**외부 API 연동 추가**
→ "어떻게" 섹션에 API 인증 방식, 응답 구조, 에러 처리를 정리. "더 공부할 것"에는 rate limit, retry 전략, 보안 등을 꺼낼 수 있음.

**리팩토링만 있음 (기능 변경 없음)**
→ "왜"를 더 파야 함. 코드 냄새(code smell), 복잡도, 가독성, 테스트 용이성 중 어떤 개선이 목표였는지.

## 안전/품질 원칙

- **민감값 유출 방지**: diff에서 API key, 토큰, 비밀번호 패턴 발견 시 문서에 포함하지 않음. 대신 "XXX 환경변수로 관리"처럼 은닉.
- **생성물 제외**: `build/`, `node_modules/`, `*.lock` 파일은 diff에 들어가도 분석 대상 아님.
- **과도한 코드 인용 금지**: 파일 하나를 통째로 붙이지 않는다. 학습이 흐려진다.
- **환각 금지**: 코드에 없는 기능을 "했다"라고 쓰지 않음. 애매하면 "~로 보임" 같은 불확실 표현 사용.
- **기존 파일 덮어쓰기 방지**: 같은 날짜/브랜치 조합으로 덮어쓰기 금지, suffix 사용.

## 빠른 예시 구조 (DotShelf 맥락)

변경: User 엔티티 + 회원가입 API + OAuth2 Google 연동

→ 문서:
- **TL;DR**: Google OAuth2로 회원가입 API 추가. `User` 엔티티 신설, `SecurityConfig`에 OAuth2 client 연동.
- **무엇을**:
  1. `User` 엔티티 + `UserRepository`
  2. `POST /api/auth/signup/google` 컨트롤러
  3. `SecurityConfig` OAuth2 설정
- **왜**: S14P31F206-110. 자체 회원가입 폼 대신 소셜 로그인 우선.
- **어떻게**:
  - Spring Security OAuth2 Client의 `authorization_code` flow 선택 이유
  - User 엔티티에 `oauth_provider` + `oauth_provider_id` 조합 unique 제약 이유
  - 신규 가입 시 기본 서재 자동 생성 훅 (`@EventListener`)
- **배운 것**:
  - OAuth2 `authorization_code` vs `implicit` vs `PKCE`의 선택 기준
  - Spring Security의 `OAuth2UserService` 확장 패턴
- **더 공부할 것**:
  - [ ] ID Token vs Access Token — 프론트에 뭘 내려줘야 하나?
  - [ ] Google refresh token rotation 전략
  - [ ] Apple/Kakao 공급자 추가 시 구조 변경 비용

## 의사결정 요약

1. 범위 확정 (기본 `origin/dev..HEAD`)
2. 커밋 + diff 수집, 생성물 제외
3. 섹션별 분석 (무엇/왜/어떻게/배운것/공부할것)
4. 템플릿에 맞춰 작성, 한국어 + 구체 예시
5. `docs/study/{YYYY-MM-DD}-{브랜치}.md`에 저장
6. 사용자 검토 → 필요 시 수정

변경이 얕거나 학습할 게 적으면 **억지로 문서를 만들지 않는다**. "이번엔 스킵하시겠어요?"를 제안한다. 학습 노트는 신호, 설정 파일 추가만으로는 신호가 약하다.
